Go 1.11 이전에는 전역 `$GOPATH/src` 아래에 모든 소스 코드를 두고 패키지를 관리(`go get`)했기 때문에, 프로젝트별로 라이브러리 버전을 다르게 가져가는 것이 거의 불가능에 가까웠다.

이를 해결하기 위해 도입된 것이 **Go Modules** 시스템이다.

---

## 1. 기본 시작하기

프로젝트 루트 디렉토리에서 모듈을 초기화한다.

```bash
go mod init <모듈_이름>
```

모듈 이름은 통상 GitHub 저장소 주소(예: `github.com/username/project`)나 패키지 경로를 지정하며, 루트 경로에 `go.mod` 파일이 생성된다.

---

## 2. 필수 명령어 정리

- **`go mod tidy`**: 코드베이스 전체를 스캔하여 import되지 않은 불필요한 의존성을 `go.mod` 및 `go.sum`에서 제거하고, 누락된 모듈을 추가한다. 개발 시 가장 빈번하게 사용한다.
- **`go mod download`**: `go.mod`에 명시된 모든 의존 패키지를 로컬 모듈 캐시(`$GOPATH/pkg/mod`)에 내려받는다. CI/CD 파이프라인에서 빌드 전 의존성 레이어를 미리 캐싱할 때 유용하다.
- **`go mod verify`**: 다운로드된 로컬 모듈의 해시값이 `go.sum`에 기록된 체크섬과 일치하는지 검증하여 무결성을 확인한다.
- **`go mod graph`**: 현재 모듈의 전체 의존성 트리를 텍스트 형태로 출력한다.
- **`go mod edit`**: CLI 상에서 직접 `go.mod` 파일의 특정 지시어(`require`, `replace`, `exclude` 등)를 수정하거나 버전을 고정할 때 사용한다.
- **`go mod vendor`**: 프로젝트 루트의 `vendor/` 디렉토리에 외부 의존성 소스 코드를 그대로 복사해 온다. 외부 네트워크가 차단된 폐쇄망 환경 빌드나 배포 시 코드베이스 자체에 의존성을 포함시킬 때 사용한다.

---

## 3. Go 1.21+ 하위 호환성과 툴체인 (Toolchain)

Go 1.21부터는 `go.mod`의 `go` 지시어 동작 방식이 한층 정교해졌다.

```go
module myproject

go 1.22
```

개발 환경에 최신 Go(예: 1.26+)가 설치되어 있더라도, `go.mod`에 `go 1.22`가 선언되어 있다면 컴파일러는 Go 1.22 시점의 언어 문법 스펙과 표준 라이브러리 동작 규칙을 그대로 흉내 내어(**Emulate**) 빌드한다.

더 나아가 시스템에 설치된 버전보다 `go.mod`에 선언된 버전이 더 높을 경우, Go 1.21 이상에서는 `GOTOOLCHAIN` 기능이 동작하여 필요한 Go 툴체인 버전을 자동으로 다운로드하여 해당 컴파일러로 빌드를 위임한다. 하위 호환성과 개발자 간 일관된 빌드 환경 보장을 언어 차원에서 강력하게 지원하는 철학이다.
