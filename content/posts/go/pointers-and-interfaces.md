Go 코드를 처음 읽을 때는 `*T`를 받는 함수에 왜 `&` 없이 변수를 넘기는지, `context.Context` 같은 타입에는 왜 `*`가 없는지 혼란스러울 수 있다. 핵심은 포인터와 인터페이스가 **함수 호출부의 표기**가 아니라 **타입의 의미**라는 점이다.

---

## 1. 포인터 인자는 호출할 때 다시 `&`를 붙이지 않는다

Go의 함수 인자는 모두 값으로 전달된다. 포인터를 인자로 전달하면 포인터 값, 즉 주소가 복사된다. 변수 타입이 이미 `*T`라면 `*T`를 받는 함수에 그 변수를 그대로 전달한다.

```go
type User struct {
    Name string
}

func rename(u *User) {
    u.Name = "Kim" // (*u).Name과 같은 필드 접근
}

func example() {
    user := &User{Name: "Lee"} // user의 타입은 *User
    rename(user)                // 포인터 값을 그대로 전달
}
```

`&user`라고 쓰면 `*User`가 아니라 `**User`가 된다. 반대로 `*user`는 포인터가 가리키는 `User` 값을 뜻한다.

- `&value`: `value`의 포인터를 만든다.
- `pointer`: 포인터 값 자체다. 같은 타입의 포인터를 받는 인자에 그대로 넘긴다.
- `*pointer`: 포인터가 가리키는 값이다.

구조체 필드 접근은 포인터든 값이든 `user.Name`처럼 점 표기법을 쓴다. 포인터 역참조가 필요한 경우 Go가 자동으로 처리하므로 `(*user).Name`이라고 매번 쓸 필요가 없다.

## 2. 포인터는 힙 할당을 뜻하지 않는다

Go에서 포인터는 객체의 메모리 위치를 가리키지만, 포인터를 사용한다고 해서 반드시 힙에 할당되는 것은 아니다. 개발자가 객체의 스택·힙 배치를 지정하는 문법 대신 컴파일러가 탈출 분석 등을 통해 배치를 결정한다. 일반적인 Go 코드에서는 포인터 산술도 허용되지 않는다.

포인터는 주로 다음과 같은 의미를 표현한다.

- 함수가 같은 객체를 공유하거나 그 상태를 수정할 수 있다.
- 값이 없음을 `nil`로 표현할 수 있다.
- 복사하면 안 되는 값이나 복사 의미가 부적절한 값을 가리킨다.

따라서 `*T`가 보인다고 무조건 “동적 할당 객체”라고 해석하면 안 된다. 포인터를 쓸지 값으로 다룰지는 객체의 의미와 API의 계약에 따라 결정한다. 포인터가 복사 비용을 항상 크게 줄인다고 단정할 수도 없다.

## 3. 포인터 타입과 인터페이스 타입 구별하기

함수 시그니처에서 타입 표기를 보면 구별할 수 있다.

```go
func worker(ctx context.Context, wg *sync.WaitGroup, stats *SafeStats) {
    // ctx: context.Context 인터페이스 타입
    // wg: *sync.WaitGroup 포인터 타입
    // stats: *SafeStats 포인터 타입
}
```

`context.Context`는 구조체가 아니라 인터페이스다. 인터페이스 타입은 필요한 메서드 집합을 표현하고, 변수에는 이를 구현한 구체 타입의 값이 들어간다. 구체 값은 포인터일 수도 있고 값일 수도 있다. 그러므로 “인터페이스는 언제나 실제 객체의 주소를 담는다”라고 이해하면 부정확하다. 인터페이스 값도 함수 인자로 전달될 때 값으로 복사된다.

```go
type Counter interface {
    Increment()
}

type counter struct {
    value int
}

func (c *counter) Increment() {
    c.value++
}

func run(c Counter) {
    c.Increment()
}

func exampleCounter() {
    run(&counter{}) // *counter가 Counter 인터페이스를 구현
}
```

함수가 `Counter`를 받으므로 호출부는 특정 구현체가 무엇인지 알 필요가 없다. 인터페이스를 가리키는 `*Counter`는 보통 필요하지 않다. 인터페이스 값 자체가 동적 타입과 그 값을 전달하기 때문이다. 다만 인터페이스가 실제 데이터를 항상 공유한다는 뜻은 아니다. 인터페이스에 저장된 구체 값의 타입과 그 타입의 복사·공유 의미가 중요하다.

## 4. 왜 호출부에서 인터페이스 표시를 따로 하지 않을까?

Go에서는 `IReader` 같은 접두사를 붙여 인터페이스 여부를 표시하지 않는다. 타입 선언을 확인하거나 IDE의 타입 정보에서 `interface`인지 `struct`인지 보면 된다. `Reader`, `Writer`처럼 `-er`로 끝나는 인터페이스 이름이 자주 쓰이지만, 이름만으로 판별하는 규칙은 아니다.

호출부에서 구체 타입을 숨기는 것은 의도된 경우가 많다. 예를 들어 함수가 `io.Reader`를 요구하면 파일, 네트워크 연결, 메모리 버퍼 중 어떤 구현이 전달되는지 몰라도 `Read` 동작만 사용하면 된다. 인터페이스는 구현체의 정체보다 필요한 동작에 의존하게 해 준다. 자세한 덕 타이핑과 타입 단언은 [Go 인터페이스와 컴파일 타임 타입 검증]({{< relref "interface-and-type-assertion.md" >}})에서 다룬다.

## 5. 간단히 기억하기

| 타입 표기 | 읽는 법 | 전달할 때 |
| --- | --- | --- |
| `T` | 값 타입 | `T` 값을 전달 |
| `*T` | `T`를 가리키는 포인터 | 이미 `*T`라면 그대로 전달하고, `T`에서 만들 때는 `&value` 사용 |
| `SomeInterface` | 메서드 집합을 만족하는 타입을 받는 인터페이스 | 인터페이스 변수 자체를 전달 |

시그니처의 `*`는 포인터 타입이라는 표시이지, 호출할 때마다 붙이는 기호가 아니다. 인터페이스 여부 역시 변수 이름이나 호출 문법이 아니라 타입 선언에서 확인한다. Go는 타입과 함수 계약에서는 이 차이를 드러내고, 실제 필드 접근이나 호출부 문법은 가능한 한 간결하게 유지한다.
