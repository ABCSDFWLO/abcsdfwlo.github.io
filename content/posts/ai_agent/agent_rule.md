# AI 에이전트 코딩 규칙 v1

## 기본 원칙

**명세가 원본(source of truth)이고, 코드는 명세에서 언제든 다시 만들 수 있는 산출물이다.** 아래 규칙은 모두 이 원칙에서 나온다.

- 사람은 명세와 테스트 벡터를 리뷰하고, 코드는 테스트로 기계적으로 검증한다.
- 에이전트가 발전할수록 명세에서 다시 생성하는 비용이 떨어진다. 따라서 장기적으로 남는 자산은 명세의 품질이다.
- 본 문서에서 MUST / SHOULD / MAY는 RFC 2119의 의미로 쓴다.

## 1. 도메인 분리

도메인 경계는 기획 단계에서 정하고, 가능하면 도구로 강제한다.

1. 도메인은 기획 단계에서 책임 단위로 정의하고, 도메인마다 디렉터리를 둔다.
2. 각 도메인은 README.md를 MUST 갖는다: 책임, 공개 접점, 의존 가능한 도메인, 적용되는 명세 목록.
3. 도메인 간 의존은 공개 접점으로만 허용한다. 가능하면 문서뿐만 아니라 도구(import 규칙 린터, 언어의 가시성 기능 등)로 강제한다.
4. 여러 도메인이 공유하는 개념(ID 형식, 시간 표현, 에러 형식 등)은 **기반 명세**에 한 번만 정의하고, 도메인 명세는 이를 참조한다.
5. 공용 코드 디렉터리는 2개 이상의 도메인이 실제로 사용할 때만 진입할 수 있고, 다른 도메인과 동일하게 명세를 갖는다. "어디에도 안 맞아서"는 진입 사유가 아니다.
6. 다음 신호가 보이면 도메인 경계를 재검토한다.
   - 기능 하나가 3개 이상의 도메인을 동시에 수정해야 한다.
   - 같은 로직이 두 도메인에 중복 구현돼 있다.
   - 순환 의존이나 공개 접점 우회가 필요해진다.

## 2. 명세

명세가 먼저, 코드가 나중이다. 임의의 개발자나 에이전트가 명세만 보고 구현해도 같은 결과가 나와야 한다.

### 2.1 대상

코드 바깥에서 관찰되거나 다른 도메인·프로그램이 의존하는 모든 경계는 명세 대상이다.

예: 파일 포맷, 데이터 스키마, API 엔드포인트, 언어별 바인딩, 도메인 공개 접점, 바이너리의 I/O 커맨드(인자, 표준 입출력, 종료 코드), 설정 파일과 환경 변수, 이벤트·메시지 페이로드, 네트워크 프로토콜.

### 2.2 작성 기준

- 산문 명세와 함께, 가능하면 기계 판독 스키마(OpenAPI, JSON Schema, protobuf 등)를 둔다. 둘이 충돌하면 기계 판독 스키마가 우선한다.
- 다음 항목을 빠짐없이 명시한다: 문자 인코딩, 엔디언, 시간 포맷과 타임존, null과 필드 없음의 차이, 최소·최대값과 크기 제한, 에러 케이스와 에러 형식.
- **보장하지 않는 것**을 명시한다 (예: 목록 정렬 순서, 에러 메시지 문구). 사용하는 쪽이 명세에 없는 동작에 기대는 것을 막기 위함이다.
- 테스트 벡터를 포함한다. 정상 케이스, 경계값, 에러 케이스를 각각 최소 하나씩 둔다.

### 2.3 변경 판정

무엇이든 고치기 전에 어느 쪽인지 먼저 판정한다.

| 상황 | 판정 | 처리 |
| --- | --- | --- |
| 코드가 명세와 다르다 | 버그 | 코드만 수정, 명세는 그대로 |
| 명세가 틀렸거나 부족하다 | 명세 변경 | 2.4의 순서를 따름 |
| 명세에 없는 동작을 결정해야 한다 | 명세 변경 | 에이전트는 멈추고 보고, 2.4의 순서를 따름 |

### 2.4 변경 순서

1. 명세 수정과 버전 올리기
2. Changelog 기록
3. 테스트 벡터 추가 또는 수정 (이 시점에 테스트가 실패하는 것이 정상)
4. 코드 수정
5. 전체 테스트 통과 확인

- 1\~3은 **명세 커밋**, 4\~5는 **구현 커밋**으로 분리한다.
- 명세 커밋은 사람의 승인을 MUST 받는다. 에이전트는 명세 변경을 제안할 수 있지만 스스로 확정하지 않는다.
- 서로 다른 작업이 같은 명세를 동시에 바꾸는 것은 피한다 (SHOULD NOT). 도메인 간 충돌처럼 여러 명세를 함께 바꿔야 하면, 하나의 작업으로 묶어 동시에 진행한다.
- **긴급 수정 예외**: 코드를 먼저 고칠 수 있다. 단, 같은 PR 안에서 명세와 테스트 벡터가 반영되기 전에는 머지하지 않는다.

### 2.5 버저닝

- 버전은 도메인 단위다. 도메인의 명세와 코드는 하나의 버전을 공유하고, 둘의 동기화는 2.4의 변경 순서로 강제한다.
- 버전은 정수 하나(v1, v2, …)로 표기하고, 바뀔 때마다 1씩 올린다. MAJOR와 MINOR는 구분하지 않는다.
- 버그 수정의 버전 처리는 버그의 크기에 따른다. 직전 버전업으로 생긴 도메인 내부 문제는 같은 버전에서 고칠 수 있고, 구조적인 버그는 버전을 올린다. 판단이 어려우면 사람이 정한다.
- 파일 포맷은 헤더에 매직 넘버와 버전 필드를 MUST 포함한다. API는 경로(`/v1/...`) 또는 헤더로 버전을 표시한다.

### 2.6 Changelog

- 도메인마다 자기 명세 디렉터리에 CHANGELOG.md를 둔다. 하나의 거대한 Changelog는 쓰지 않는다.
- 형식은 Keep a Changelog를 따른다: 버전, 날짜, Added / Changed / Deprecated / Removed / Fixed.
- 기능을 삭제하면 명세는 먼저 Deprecated로 표시한다. 명세 삭제는 그 뒤에 별도로 한다.

## 3. 테스트

테스트는 명세를 검증하는 보조 수단이다. 명세와 충돌하면 명세가 우선한다.

1. 운영 코드는 테스트를 위한 코드, 의존성, export를 포함하지 않는다 (MUST NOT). 테스트에서 내부 접근이 필요하면, 테스트 빌드에만 포함되는 파일로 노출한다.
2. 테스트는 가능하면 구현 세부가 아니라 명세의 동작을 검증한다 (SHOULD). 명세에 테스트 벡터가 있으면 그것을 입력으로 쓴다.
3. 테스트 코드는 도메인 코드와 함께 둔다. 명세 디렉터리에는 테스트 벡터(데이터)만 두고, 테스트 코드는 두지 않는다.
4. 테스트는 빠른 테스트와 느린 테스트로 나눌 수 있다 (MAY). 나눴다면 에이전트는 작업 중 빠른 테스트를, 완료 전 전체를 돌린다.

## 4. 재작성 정책

실데이터가 생기기 전에는 개선보다 삭제 후 재작성을 우선하고, 그 전환 시점은 명시적으로 정한다.

| 단계 | 명세 상태 | 호환성 | 재작성 |
| --- | --- | --- | --- |
| 실데이터 이전 | draft | 보장하지 않음 | 기본 전략. 부분 개선보다 우선 |
| 실데이터 이후 | stable | 하위 호환 MUST, 깨지면 마이그레이션 MUST | 가능. 단 기존 테스트 벡터 전체 통과 조건 |

1. 프로젝트마다 “실데이터가 쌓이기 시작하는 시점”을 구체적인 사건으로 정의한다 (예: 최초 외부 배포, 최초 사용자 저장 파일 생성). 이 사건이 일어나면 해당 명세의 상태를 stable로 바꾼다. 현재 상태는 명세 상단에 표시한다.
2. 재작성 단위는 **도메인 전체**이다. 한 도메인 안에 새 코드와 옛 코드가 섞인 부분 재작성은 하지 않는다.
3. 재작성 전에, 다른 도메인이 명세에 없는 동작에 기대고 있는지 점검한다. 발견되면 그 동작을 명세에 넣거나 “보장하지 않음”으로 명시한 뒤 진행한다.
4. 재작성은 명세와 테스트 벡터만 입력으로 한다. 기존 코드를 참고해야만 구현할 수 있다면, 명세가 부족하다는 신호다.
5. stable 이후에는 이전 버전의 테스트 벡터를 지우지 않는다. 하위 호환과 마이그레이션은 이 벡터로 검증한다.

## 5. Secret

secret은 개발자가 수동으로 주입하고, 에이전트는 값에 접근할 수 없어야 한다.

1. secret은 `secrets/` 디렉터리에만 두고, 버전 관리에서 제외한다 (`.gitignore`).
2. 에이전트의 권한 설정에서 `secrets/`의 읽기와 셸 접근을 MUST 차단한다. 문서로 “읽지 말 것”이라고만 쓰는 것은 충분하지 않다.
3. `secrets.example`에 필요한 키 이름, 형식, 용도만 명세한다. 값은 넣지 않는다. 에이전트는 이 파일을 보고 코드를 작성한다.

## 6. 에이전트 운영

에이전트에게는 짧은 지침과 명확한 멈춤 조건, 스스로 확인할 수 있는 완료 기준을 준다.

### 6.1 지침 파일

- 루트 AGENTS.md(또는 CLAUDE.md)에는 이 문서의 핵심 규칙만 둔다.
- 도메인별 규칙은 해당 도메인 디렉터리의 로컬 지침 파일에 둔다.
- 린터나 권한 설정으로 강제할 수 있는 규칙은 문서에서 빼고 도구로 옮긴다.

### 6.2 멈추고 보고해야 하는 상황

에이전트는 다음의 경우 코드를 작성하지 않고 멈춘 뒤 보고한다.

- 명세에 없는 동작을 결정해야 한다.
- 두 명세가 서로 모순된다.
- 작업을 위해 다른 도메인의 내부를 수정하거나 공개 접점을 우회해야 한다.
- 테스트 벡터를 수정해야만 테스트가 통과한다.
- secret이나 새 외부 의존성이 필요하다.
- 삭제 후 재작성이 필요하다고 판단된다 (제안은 하되, 실행은 승인 후).

### 6.3 완료 기준

- [ ] 전체 테스트 통과
- [ ] 린트와 import 규칙 통과
- [ ] 동작이 바뀌었다면 명세, 테스트 벡터, CHANGELOG가 함께 갱신됨
- [ ] 명세 커밋과 구현 커밋이 분리됨
- [ ] 도메인 README의 공개 접점 목록이 실제와 일치

## 부록: 권장 디렉터리 구조

명세를 최상위 `specs/`에 모으면, 에이전트 권한 설정에서 “명세는 읽기만 허용”을 경로 하나로 걸 수 있다.

```
/
├─ AGENTS.md              # 핵심 규칙만
├─ README.md              # 프로젝트 개요
├─ specs/
│  ├─ foundation/         # 기반 명세 (ID, 시간, 에러 형식)
│  │  ├─ spec.md
│  │  └─ CHANGELOG.md
│  └─ <domain>/
│     ├─ spec.md
│     ├─ schema/          # OpenAPI, JSON Schema, proto 등
│     ├─ vectors/         # 테스트 벡터 (golden file)
│     └─ CHANGELOG.md
├─ domains/
│  └─ <domain>/
│     ├─ README.md        # 책임, 공개 접점, 의존 가능 도메인
│     ├─ AGENTS.md        # 도메인 로컬 지침
│     └─ src/
├─ secrets.example        # 키 이름·형식·용도만
└─ secrets/               # .gitignore, 에이전트 접근 차단
```

## 부록: 명세 템플릿

`specs/<domain>/spec.md`의 기본 골격이다. 해당 없는 섹션은 지우지 말고 “해당 없음”으로 남긴다.

```markdown
# <domain> 명세

- 버전: v1
- 상태: draft | stable

## 목적과 범위
이 명세가 다루는 것과 다루지 않는 것.

## 용어
기반 명세에 없는 용어만 정의한다.

## 형식
데이터 구조, 필드, 인코딩, 크기 제한. 기계 판독 스키마는 schema/ 참조.

## 동작
입력별 기대 동작, 에러 케이스와 에러 형식.

## 보장하지 않는 것

## v(N-1)로부터의 변경
직전 버전 대비 바뀐 점, 호환성 영향, 마이그레이션 방법. v1이면 “해당 없음”.

## 테스트 벡터
vectors/의 파일 목록과 각 벡터가 검증하는 항목.
```
