> "브랜치? 대충 필요할 때 따서 쓰면 그만이지."
> "충돌(Conflict)? 손으로 풀면 되는데 뭐가 문제임?"
> "PR? 그런 건 기여 규정 빡빡한 오픈소스쟁이들이나 쓰는 절차주의 뭐시기 아닌가?"

혼자(또는 소규모로) 개발할 때 누구나 한 번쯤 품어봤을 생각입니다. 저 역시 그랬습니다. `main` 브랜치 하나 냅두고 기분 내키는 대로 딱 `feature` 브랜치까지만 마구잡이로 파서 작업하다가 머지하면 그만이라는 패기로 살아가고 있었습니다.

그러던 어느 날, 평화롭던 제 로컬 저장소에 대참사가 일어났습니다.

---

## 1. 지옥의 서막: "main을 feature에 머지하면 되는 거 아님?"

사건의 발단은 꽤 오래 묵혀둔 `feature` 브랜치 하나였습니다.

그동안 `main` 브랜치에 코어 로직들을 예쁘게 쌓아두었는데, 이 오래된 `feature` 브랜치에도 최신 코어를 반영하고 싶었던 겁니다. 그래서 아무 생각 없이 비장하게 명령어를 날렸습니다.

```bash
# feature 브랜치에서
git merge main

```

"어차피 최신 내용 당겨오는 거니까 이러라고 Git이 있는 거겠지?"

별다른 경각심 없이 며칠 동안 작업하며 이 짓을 몇 번 더 반복했습니다. 심지어 기획자 친구의 커밋까지 여기저기 섞여 들어가며 여러 브랜치를 마구 차원 이동하듯 넘나들기 시작했습니다.

그리고 마침내 작업을 합치려고 VS Code의 **Git Graph** 익스텐션을 켰을 때, 눈앞이 새하얘졌습니다.

**"어...? 내 main 브랜치가 어디 갔지?"**

스크롤을 내려도 내려도 끝없이 얽혀 있는 형형색색의 선들, 브랜치가 갈라졌다가 다시 기어들어오고 또 나가는 **무한 꽈배기 지옥도**가 펼쳐져 있었습니다. 기획자 친구의 커밋과 제 작업 커밋이 뫼비우스의 띠처럼 엉켜서, 대체 어디서부터 머지 각을 잡아야 할지 도무지 감조차 안 오는 상황이었습니다.

결국 다급하게 AI를 붙잡고 헬프를 쳤습니다.

그리고 알게 되었습니다. '오래된 브랜치에 main을 습관적으로 머지해 가며 작업하는 행위'는 불법까진 아니더라도, 깃 그래프를 믹서기에 갈아버리는 대표적인 안티 패턴이었다는 사실을요.

---

## 2. "커밋이 자세할수록 좋은 거 아닌가?"라는 착각

그전까지 저는 PR(Pull Request)이 무슨 원리로 돌아가는지도, 왜 사람들이 `Squash`나 `Rebase`에 목을 매는지도 전혀 몰랐습니다.

솔직히 속으로 이렇게 생각했습니다.

> *"커밋이 많아야 히스토리를 더 자세하게 볼 수 있는 거 아님? 그걸 왜 하나로 뭉개?"*

완벽한 착각이었습니다. 혼자 개발할 때 쌓이는 실제 커밋 로그를 까보면 이런 식이기 때문입니다.

```text
commit 7f3a1b: feat: 로그인 버튼 구현
commit 8c2d4e: fix: 오타 수정
commit 1a9f0c: fix: 진짜 수정
commit 3e5b7a: test: 콘솔 찍어봄
commit 9d4e2f: fix: 최최종
commit 4b6c8a: fix: 최최최최종_진짜_마지막

```

히스토리가 자세한 게 아니라, **아무 영양가 없는 쓰레기 커밋 노이즈가 프로젝트 전체 역사를 도배하고 있었던 것**입니다. 나중에 어떤 버그가 생겨서 이전 코드를 추적하려 해도, 수십 개의 '최종' 커밋 사이에서 길을 잃을 수밖에 없는 구조였습니다.

## 3. 뇌 정지 오고 나서야 깨달은 PR의 본질

머지 지옥을 겪고 강제로 깃을 공부하면서 세 가지 사실을 뼈저리게 깨달았습니다.

### ① PR은 '기능 단위의 컨테이너'다

커밋이 20개든 30개든 상관없습니다. PR을 열면 "이 기능(feature)에서 정확히 어떤 파일의 몇 줄이 바뀌었는가"를 웹 화면(Files changed)에서 한눈에 모아서 볼 수 있습니다.

터미널에서 눈알 빠지게 `git diff`를 치지 않아도, 내가 삽질하며 남겨둔 `console.log`나 불필요한 주석을 머지 직전에 셀프로 검거할 수 있게 됩니다.

### ② Squash and Merge의 마법

`Squash and Merge`는 브랜치에서 지지고 볶았던 그 모든 자잘한 커밋(오타 수정, 테스트 콘솔 등)을 **단 1개의 깔끔한 기능 커밋으로 압축해서 `main`에 합쳐줍니다.**
덕분에 `main` 브랜치의 히스토리는 마치 잡지 목차처럼 아름답고 직관적으로 남습니다.

```text
# Squash and Merge 후 main 브랜치의 평화로운 히스토리
- feat: 카카오 소셜 로그인 연동 (#12)
- feat: 결제 실패 예외 처리 추가 (#13)
- fix: 모바일 화면 네비게이션 깨짐 현상 수정 (#14)

```

### ③ main 브랜치는 '잠가야' 제맛이다

아무리 머리로 "조심해야지" 다짐해도 새벽에 피곤하면 또 `main`에 바로 커밋 치고 푸시를 날립니다.

저장소 설정에서 `main`을 잠가버리면(Branch Protection), 내 손가락이 미쳐 날뛰어도 GitHub가 "어허, PR 만들어라" 하고 튕겨내 줍니다. PR은 남을 감시하는 도구가 아니라, **미래의 피곤한 나로부터 코드를 지키는 물리적 안전벨트**였던 셈입니다.

## 4. 실전: 복잡한 룰 없이 딱 이것만 지키는 워크플로우

Git-flow처럼 `develop`, `release`, `hotfix` 등 거창한 브랜치를 대여섯 개씩 쪼갤 필요는 없습니다. 1인/소규모 개발에서는 아래 3단계 규칙만 지켜도 꽈배기 참사를 100% 예방할 수 있습니다.

### Step 1. main 브랜치 다이렉트 푸시 금지 (잠금 설정)

GitHub 저장소의 `Settings` → `Branches`에서 protection rule을 추가합니다.

* **Require a pull request before merging**: 체크
* **Do not allow bypassing the above settings (Include administrators)**: 체크 (관리자인 나도 예외 없이 잠금)

### Step 2. 작업은 항상 최신 main에서 딴 새 브랜치에서만

```bash
# 항상 main을 최신화하고 브랜치 분기
git switch main
git pull origin main
git switch -c feature/cool-feature

```

### Step 3. 머지는 무조건 GitHub PR에서 'Squash and merge'

1. 원격에 브랜치 푸시: `git push origin feature/cool-feature`
2. GitHub에서 `Compare & pull request` 클릭
3. **Files changed** 탭에서 변경점 최종 셀프 체크
4. 머지 버튼 옆 드롭다운에서 **Squash and merge** 선택 후 완료
5. 로컬로 돌아와 브랜치 정리:
```bash
git switch main
git pull origin main
git branch -d feature/cool-feature

```



> **Q. 작업 중인 feature 브랜치가 너무 오래돼서 최신 main 코드가 필요하면 어떡하나요?**
> `git merge main`을 무지성으로 때려 꽈배기를 만들지 말고, feature 브랜치에서 `git rebase main`을 사용해 베이스를 최신으로 옮겨주거나, 가능하면 feature 브랜치의 작업 범위를 작게 쪼개서 애초에 PR을 빠르게 닫는 것이 가장 깔끔합니다.

---

깃을 처음 배울 때 넘쳐나던 수많은 브랜치 전략과 룰들은 여전히 보일러플레이트처럼 느껴질 수 있습니다.

하지만 딱 하나, "main은 잠그고, 작업은 브랜치에서 해서 PR로 모아 Squash 머지한다"는 공식만큼은 협업 여부를 떠나 개발자의 정신 건강과 프로젝트 수명을 위한 가장 최소한의 안전장치입니다.
